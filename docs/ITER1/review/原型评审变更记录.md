## 全局 UI 设计原则

**P1 助手优先**：大部分用户操作的入口是助手页面，用户通过输入文字、上传文件完成操作（如创建待办）。菜单栏里的各页面是手动操作入口，面向有经验、需要精细调整或批量处理的用户。

- 评审和设计每个功能时，先回答“能不能在助手页完成”；常用操作必须能在助手页完成。
- 手动页面保留完整功能，但不作为主要路径来设计引导。
- 适用于全项目，编写需求文档时写入总体设计原则。

## 1. 简化手动设置日期、时间、时长

**目标**：缩短手动创建、编辑待办时设置时间的操作路径。

**范围**：待办页“新建待办”弹窗、右侧待办详情面板。

1. **从待办内容识别时间**：复用首页 `parseWhen` / `parseDur` / `parseLocation` 的识别逻辑。输入“明天下午3点开会 1小时”时自动填好日期、时间、时长，并标出识别到的文字。识别结果可手动修改；用户手动改过的项，后续输入不再覆盖。
2. **日期快捷选项**：`今天` `明天` `后天` `本周六` `下周一` `选择日期…`（最后一个才打开日历）。
3. **时间快捷选项**：`全天` `09:00` `10:00` `14:00` `15:00` `20:00` `自定义`。
   - 选“全天”时隐藏时长。
   - 点“自定义”时出现时间输入，按 15 分钟对齐。
4. **时长**：保留 v2 的快捷选项（15 分钟、30 分钟、45 分钟、1 小时、2 小时）和拖动色条。
5. **结果行**：下方显示设置结果，例如“10月26日（周日）14:00–15:00”。
6. **默认值**：日期默认留空（进入“未排期”），与 v2 一致；从日历视图点空白处新建时，带入点击的日期和时间。

## 2. 手动新建待办时直接上传附件；重复文件处理

### 2.1 直接上传

- 附件区放两个入口：`⬆ 上传文件`（支持拖入）和“从知识库选择”。去掉 v2 的“创建后上传新附件”勾选项。
- 选好文件后立即上传，表单内显示每个文件的进度；不必等上传完成就可以点“创建”，完成后自动关联到这条待办。
- 上传的文件同时保存到个人知识库，占用存储配额（与 v2 一致）。
- 上传后取消表单：文件**保留在知识库**，提示“已上传的 N 个文件保留在知识库中”。理由：文件已占配额并完成识别，删除可能误删用户想要的文件。
- 上传限制（类型、单文件大小、单次数量和总大小、配额）沿用文件库的规则。

### 2.2 重复文件处理

**原则**：同一用户的同一份文件只存一份，多条待办引用它。是否重复按**内容指纹 SHA-256**判断（在浏览器计算），只在本人的文件内比对，不看文件名。原型用“文件名 + 大小”模拟。

| 情况 | 处理 |
|---|---|
| 1. 知识库里已有这份文件 | 不重复上传，直接关联已有文件，提示“已在知识库中，直接关联”。（v2 已有） |
| 2. 另一个页面正在上传同一份文件 | 不再上传；等那边完成后，把文件同时关联到两条待办，提示“另一个页面正在上传该文件，完成后自动关联”。（v2 缺失，需补上） |
| 3. 两个页面几乎同时开始上传 | 服务端兜底：数据库对“用户 + 指纹”加唯一约束，后到的请求直接拿到已有文件的编号，配额只算一次。（设计阶段实现，原型只写说明） |
| 4. 内容相同、文件名不同 | 算重复，按情况 1 处理，提示“与知识库中的《X》内容相同”。 |
| 5. 文件名相同、内容不同 | 不算重复，两份都保存，知识库里显示的文件名自动加后缀，例如“报告(1).pdf”。 |
| 6. 同一文件给同一条待办加了两次 | 直接忽略，不报错。 |

- 一个页面上传完成后，其他打开着的页面里，知识库列表自动刷新。

## 3. “已归档”更名为“已删除”

v2 的“归档”实际是可恢复的删除（回收站），叫“归档”容易和“已完成”混淆。

1. **名称统一**：标签“已归档”→“已删除”；按钮“归档”→“删除”；日历视图“显示已归档”→“显示已删除”；首页意图标签、示例说法、页面提示和操作日志类型里的“归档待办”→“删除待办”。
2. **首页识别**：增加“删除”关键词；“不做了”“不用做”“取消”等说法继续识别为删除。
3. **“全部”不含已删除**：“全部”= 未完成 + 已完成；已删除的只在“已删除”标签中查看。
4. **删除不弹二次确认**：删除后提示“已删除 · 撤销”。提示文案：“删除后不再出现在待办列表和提醒中，可在‘已删除’中恢复。附件仍保留在知识库中。”
5. **彻底删除**：在“已删除”中提供手动“彻底删除”，必须二次确认，不可恢复；只删待办及其与文件的关联，不删知识库文件。
6. **不做自动清除**（如 30 天后自动删除）。理由：待办数据量很小，自动清除容易让用户以为数据丢失。
7. 数据状态值由 `archived` 改为 `deleted`，演示数据同步修改。

## 4. 助手优先的落地

依据全局原则 P1。v2 助手页的不足：上传文件与文字输入无关，助手创建的待办没有附件；操作结果只能看，后续操作要去待办页；待确认会议要去待确认页处理。

- **A. 文字 + 附件一起发送**：点“上传文件”或拖入文件后，文件以小卡片挂在输入框内，可移除。发送时：
  - 只有文字：同 v2。
  - 文字 + 文件（如“下周三前看完这份合同”）：创建待办并关联附件。
  - 只有文件：存入知识库；会议录音照常进入待确认；其他文件由助手问“要为它建一条待办吗？”
  - 上传限制和重复文件处理按第 2 项。
- **B. 结果卡片可继续操作**：待办卡片带 `修改` `完成` `删除` `撤销`；缺少日期等信息时助手在对话中追问，不引导去表单。
- **C. 在助手页处理待确认会议**：点“待确认会议 N 个”后在对话中展开会议摘要和识别出的待办，可逐条确认。
- **D. 菜单栏保留、结构不变**：原则靠助手页的能力落实，不靠隐藏菜单；登录后默认进入助手页（v2 已如此）。

## 5. 个人知识库：文件夹改为标签

**目标**：一个文件可以有多个标签；保持“小白 10 分钟上手”。思路是标签由系统管，用户只需会“看”和“偶尔改一下”。

### 5.1 标签与界面

1. **自动打标签**：文件管理模型为每个文件打 1～3 个标签，优先用已有标签和预设标签库，确有需要才新建。
2. **层级写在标签名里，最多两层**：如“工作/报告”，侧栏自动显示为树；没有单独的层级管理操作。父标签数量按文件去重。
3. **普通用户只有“改标签”**：文件行上显示标签小块，点 × 去掉，点 ＋ 输入（自动补全已有标签，没有就新建）。v2 的“移动”对话框改为此操作。
4. **高级入口“管理标签”**（知识库页右上角，不显眼）：改名、合并、删除；删除标签不删文件。另有“重新生成标签”（见 5.3）。
5. **助手可操作**：如“把这份合同加上报销标签”“找工作里的报告”。
6. **侧栏**：顶部“全部文件”，末尾“未打标签”；单选筛选，不做多标签组合筛选（用搜索或助手）。底部说明改为“标签由文件管理模型自动生成，可以随时修改；一个文件可以有多个标签。”
7. 数据：文件的 `folder` 改为 `tags` 数组。

### 5.2 预设标签（面向 20～55 岁：大学生、白领、家庭主妇、小老板）

预设标签是**候选库，默认不显示**；某个标签第一次被用到才出现在侧栏，用户只看到和自己相关的标签，注册时不增加步骤。

| 一级 | 二级 | 主要人群 |
|---|---|---|
| 工作 | 会议、报告、方案、合同协议、模板、项目资料 | 白领、小老板 |
| 生意 | 客户、供应商、订单、进货库存、员工、资质证照 | 小老板 |
| 学习 | 课程、考试、论文、读书笔记、证书 | 大学生、白领 |
| 求职 | 简历、面试、录用通知 | 大学生、白领 |
| 财务 | 账单、发票报销、税务、理财、工资社保 | 全部 |
| 家庭 | 孩子教育、老人照护、宠物、菜谱、家庭账本 | 家庭主妇、白领 |
| 生活 | 健康医疗、证件、保险、房屋租住、出行旅游、照片 | 全部 |
| 资料 | 视频、收藏、参考 | 全部 |

- 个人设置增加可选的“我的身份”（大学生 / 白领 / 家庭主妇 / 小老板，可多选、可不填），只用于让模型优先用对应标签。
- 预设标签可改名、删除。

### 5.3 整体重新生成标签

- 用户手动调整标签后**不触发**整体重新生成；新上传的文件仍自动打标签，只归入已有标签（增量）。
- 只在用户主动要求时整体重新生成，必须满足：
  1. 用户手动添加的标签不能被删除；
  2. 用户手动指定过标签的文件，其标签不能修改；
  3. 按用户手动指定标签的风格完成重新生成。
- **第 1、2 条由程序保证，不依赖模型**：
  - 每个标签记录来源（用户 / 模型）；用户手动改过标签的文件标记为“锁定”。
  - 重新生成时锁定的文件不发给模型；用户建的标签不允许删除。服务端校验模型输出，违反规则的结果丢弃。
  - 用户主动删掉的模型标签记入“不再使用”名单，重新生成时不再加回。
  - 生成后先**预览差异**（新增 / 合并 / 删除的标签，每个文件的变化），确认后才生效；提供“撤销上次重新生成”。
- **第 3 条分两步**：
  1. 整理标签体系：以用户手建的标签、锁定文件及其标签、改名和合并记录为示例，归纳风格（粗细、名称长短、口语或正式、层级习惯），输出新的标签体系。
  2. 给文件打标签：每批几十个文件，用 `json_schema` 枚举限定只能从第 1 步的标签中选。
- **模型建议（暂定，后续在需求或实际使用中调整；系统本身支持配置不同 LLM）**：
  - 第 2 步用 DeepSeek Flash：调研结论“文件归类够用”，且选项已限定。
  - 第 1 步建议用 Kimi K3.1 Pro（调研中的推荐替代：大陆可直连、100 万 token 上下文、支持 `json_schema` + strict），备选 `qwen3.8-max`。这一步要综合几百个文件归纳风格，小模型容易前后不一致；只在用户主动要求时运行，成本影响小。
  - 未实测；Kimi 价格未查到。建议设计阶段用约 50 个文件、三种不同风格的手动标签做一次小测试再定。
  - “模型与服务”页增加可选的“标签整理模型”，默认 Kimi，未配置时退回主模型。

### 5.4 待办使用标签（轻量）

- 与文件共用同一套标签；待办创建时由模型按内容和附件标签自动打标签。
- 待办列表可按标签筛选；详情面板中可改标签。
- 新建表单不增加标签字段（保持第 1 项简化后的表单）。
- 整体重新生成只针对文件，不改待办。

## 6. 近 3 天提醒合并进助手页（试行，看效果再定）

v2 的问题：邮件设置卡片占大块位置；每条两行且显示无用的来源信息；与待办列表的日期分组重复。

- 菜单去掉“近 3 天提醒”；红色数字移到“助手”。
- 助手页增加“近 3 天”区域：已逾期（有才显示）、今天、明天、后天。每条一行：`○ 时间段 标题 📍地点 📎N`，点标题打开详情；不显示来源。
- 已逾期条目带快捷按钮 `改到今天` `改到明天`。
- 邮件提醒设置移到个人设置；区域底部只留一行“每天 08:00 发邮件提醒 · 设置 · 预览邮件”。
- 排序：条目很少（新用户）时“试试这些说法”在前；有待办后“近 3 天”在前。
- 备选方案（试行效果不好时）：保留独立页，只做“精简为一行、去掉来源、邮件设置移走”。

## 7. 完成待办的操作路径

1. **统一圆形勾选框，一键完成**：列表、议程、助手页“近 3 天”、日历周/日视图的待办块（悬停显示）。完成后显示删除线、变淡，提示“已完成 · 撤销”，几秒后移出未完成列表；不弹确认。
2. **助手单条完成直接执行**：只匹配到一条时直接完成，结果卡片带“撤销”；匹配到多条时让用户选。
3. **助手批量完成用确认卡片**（一次完成 ≥2 条）：
   - 例“今天的事儿，我都完成了”：范围为今天的未完成待办（含全天）；还没到时间的照样勾选并提示“还没到时间”；已逾期的折叠列出、默认不勾选。按钮“完成 N 项”；完成后“已完成 N 项 · 撤销”，一次撤销全部恢复。
   - 例“今天除了买保险的事儿，都搞完了”：排除条件在标题、地点、备注、标签、附件名中匹配，并写明排除原因（命中的字段和内容）；用户可手动改勾选。
   - 排除条件没有匹配到任何待办时，不静默全部完成：说明“没有找到和‘X’相关的待办”，并默认全部不勾选。
4. **每日提醒邮件里每条待办带“完成”链接**（免登录、签名、有有效期的一次性链接）：原型中在邮件预览里展示；是否实现在需求阶段决定。

## 8. 没有日期的待办：“待安排”

- **概念**：“待安排”不是新的数据类型，就是还没有具体日期的待办。v2 中“无日期”（列表分组）和“未排期”（日历侧栏）统一改名为“待安排”。
- **星标**：只有“重要”一种；星标的排在前面。
- **不做子步骤**（用户判断：这类事项用户不会喜欢子步骤管理）。
- **备注 + 想法记录**（参考调研 `docs/ITER1/research/2026-10-25-任务备注与记录流设计调研.md`：主流个人产品没有用记录流完全替换备注；Todoist、滴答清单是“备注 + 时间顺序记录”并存，均为大众产品）：
  - 所有待办保留单一“备注”（长期不变的说明）。
  - “想法记录”：追加式、带时间戳、可带附件；新的在上。有日期的待办只显示“＋ 追加想法”入口，有记录后才展开；待安排事项中明显展示。
  - 助手中说“XX 那件事，再记一下：……”追加到对应事项。文字中的网址自动变成链接。想法里带的附件同时归入事项附件。助手知识查询可搜到想法记录。
- **附件**：沿用第 2 项（直接上传 / 从知识库选择）。
- **列表显示为卡片**：标题、最新想法开头、📎 数量、⭐、“N 天前更新”。排序：星标 → 期限近的 → 最近更新。
- **定期提醒**：每周一提醒邮件和助手页提示“你有 N 件待安排的事，要排进这周吗？”，助手可按日程空档建议时间；超过 30 天没有动静的事项顺带问“还要做吗？”。
- **排上日期**：拖到日历、详情中日期快捷选项、对助手说“把 X 排到周六上午”。排上后想法和附件随之保留。

## 9. 时间识别与归类

- 不需要大模型判断“想法还是待办”。大模型只负责**提取时间及精度**（具体到日 / 周 / 月 / 无），程序按规则归类：

| 说法 | 提取结果 | 归到 |
|---|---|---|
| 下周三交月报 | 具体日期，无时间点 | 有日期的待办（全天） |
| 下周三下午3点交月报 | 具体日期 + 时间 | 有日期的待办 |
| 下个月要买车险 / 月底前 / 这周内 / 年底前 | 时间段 | 待安排，带“期限” |
| 想研究一下保险 | 无时间 | 待安排，无期限 |

- **期限（时间段）**：待安排事项可带期限，如“11月内”“本周内”。期限最后 7 天进入助手页“近 3 天”区域（如“本月内要完成：买车险（还剩 7 天）”），并出现在每周一的待安排提醒中。定具体日期后变成普通待办。
- **结果卡片写清归到哪里**，并写出具体日期（避免“下周三”的歧义），带 `设具体日期` `撤销`。
- **可追问不强制**：如“车险几号到期？告诉我可以按到期日提醒你”，用户不答也照常创建。

## 10. 助手页对话化（v3 评审，2026-10-26 确认）

**背景**：请一位朋友试用 v3。他先看了个人设置，又在“待确认”页停留但看不懂这个页面的用途，在知识库页停留很久，却不知道可以按意思查询，也没想到待办也能按意思查询并直接操作。助手页他只看了约 5 秒，之后再没打开。结论是：用户按传统软件的习惯逐个点菜单，不知道能对话，也不知道对话能做什么。只在页面上加一句说明文字不够。

**样例**：`public/ITER1/samples/chat-home.html`，线上地址：

https://daily-assistant-proto.accrepo.com/ITER1/samples/chat-home

1. **整页改为对话，助手先开口**
   - 助手有名字和头像（默认“小禾”，可改名），页头显示名字和“你的私人助手 · 帮你记事、找文件”。视觉朴素，像聊天软件，不用 AI 风格的渐变、发光。
   - 打开页面时，助手按时段问候，并在消息里带出今天的待办卡片，可以直接打勾完成。
   - 有逾期时，助手单独发一条消息，附 `改到今天` `改到明天` `已经交了` 按钮。
   - 回复前显示约 0.5 秒的“正在输入”，增加真人感。
   - 用户的话和助手的回复按聊天气泡往下排；操作结果用卡片展示，带 `撤销` `修改`。
2. **会议录音整理结果由助手主动发消息**：例如“你昨天上传的周会录音，我整理出 4 条待办，有 1 条是分给你的。要一起过一下吗？”在对话里逐条勾选后加入待办，可以“听原话”（显示原文和时间点）。选“晚点再说”时，助手稍后再提醒一次。替代第 4 项 C。
3. **取消“待确认”菜单项**：用户看不懂这个页面，它的功能由第 2 点承担。
4. **不做首次引导教程**：用户认为大部分人不会看，手机 App 上更是如此。改为**随用随提示**：每种能力第一次用完后，在助手回复底部附一行 💡 提示，教相关的说法；同一种提示只出现一次。示例：
   - 查完文件：“我只在你自己上传的文件里找，而且是按意思找，不用记文件名和关键字。”
   - 记完一件事：“说错了直接补一句就行，比如‘改到下午4点’。”
   - 批量推迟后：“也可以说‘除了周会，明天的都推迟’。”
   - 按意思查到待办后：“查到后可以接着说‘把重疾险排到周六上午’。”
5. **建议说法**：输入框上方一排可点击的说法，点一下直接发送，可以横向滑动。内容覆盖记事、查文件、按意思查待办、批量推迟、批量完成。输入框提示文字口语化：“跟我说就行，比如：周五3点体检”。语音按钮放在输入框内，比 v3 更显眼。
6. **“最近安排”按钮**（替代第 6 项的“近 3 天”区域，以及右上角的摘要标签）：
   - 位置：输入框正上方，在建议说法那一行的最左边，固定不动，不跟着建议说法滑动。整个页面只有这一个入口。
   - 样式：浅蓝底、蓝色粗体字“📅 最近安排 N”，N 是今天还没完成的件数。有逾期时，按钮右上角显示红色角标和逾期件数。建议说法是白底灰框，两者在样式上区分开。
   - 点击后在输入框上方弹出面板（手机上是底部弹出），依次列出已逾期、今天、明天、后天、期限快到的事项，可以直接打勾。底部有 `去待办页 ›`、待安排件数，以及邮件提醒设置的入口。点 ×、点面板外面或再点一次按钮都会关闭。
   - 面板内容**不发进聊天记录**：这是高频查看的动作，每次都插一张大卡片会让对话很乱。
7. **左侧菜单默认收成图标栏**，不隐藏。鼠标移上去显示名称，点底部的 » 展开，展开后记住用户的选择。手机上不显示左侧菜单。修订第 4 项 D：菜单仍然保留，但让出视觉主体。

8. **对话记录**：默认只显示当天的对话，往上翻可以看更早的；历史记录保留 30 天。
9. **问候频率**：每天第一次打开时完整问候（今天的事、逾期的事、待处理的会议）；当天再打开时只补充有变化的内容（如“又有 1 件到期了”），没有变化就不说话。
10. **问候语生成**：程序按“固定模板 + 待办数据”组好内容，再由内嵌大模型改写成自然的问候，可以带节日、天气等开场，例如“端午节好，今天……”。规则：
    - 节日由程序查日历后告诉模型（含农历节日），不让模型自己判断。
    - 件数、时间等事实以程序数据为准，模型只负责语气；程序校验模型输出中的数字和时间。
    - 模型约 2 秒内没有回应或出错时，改用固定模板。
    - 每个用户每天只生成一次完整问候并缓存。
11. **各菜单页放“问助手”入口**：知识库搜索框改为“用一句话描述你要找的内容”，并注明是按意思找；待办页顶部放一句示例说法，例如“跟助手说：把这周所有会议推迟一天”。在这些入口输入后，跳到助手页，在对话里处理。

12. **助手主动提出代写文档**（用户 2026-10-26 提出，同日确认范围）

- **场景**：
  - 新增待办“下周三交周报”：助手问“需要我参照之前的周报帮你写吗？可以把本周素材发给我。”
  - 会议录音中出现“编写一份新的 XX 项目介绍”：助手提示“知识库里有类似的项目介绍，把项目信息给我，我来写。”
- **做法**：
  1. 识别写作类任务，如周报、方案、介绍、总结、报告。
  2. 在本人知识库里按意思找类似文档，作为格式和写法参考。
  3. 收集素材。周报可以先自动整理本周已完成的待办、会议要点和想法记录，再问用户要不要补充；项目介绍先从会议录音里提取项目信息，再请用户补充。
  4. 生成初稿。
- **提示规则**：
  - 每件事只提示一次，带 `好，开始` `不用了`。
  - 同类事项连续拒绝 3 次后，不再主动提示这一类。
- **范围建议**：
  - 只写文字稿：初稿在对话中显示，可复制，可导出 Word；同时存入知识库，并挂到对应待办上。
  - 不生成 PPT，也不做复杂排版。
  - 数字和事实只能来自用户素材和知识库；素材不足时明确说出缺什么，不自行编造。
- **影响**：
  - 属于新增能力“代写文档”，需求文档中单独列出。
  - 依赖 Office 文档文字抽取：原待定决定“V1 是否抽取 Office 文字”已定为 **V1 必须支持**。

## 11. 菜单收起/展开按钮太小（v4 评审，2026-10-27 提出）

**问题**：v4 左侧菜单底部的收起/展开按钮只是一个文字字符“»”/“«”，12px 灰字，放在深色菜单栏最下方，几乎看不出来是按钮，用户很难发现菜单可以展开。

**改法（建议）**：
1. 改用图标，不用文字字符：展开状态用“收起侧栏”图标，收起状态用“展开侧栏”图标（侧栏框 + 箭头样式），图标大小与上面的菜单图标一致（约 18–20px）。
2. 点击区域与菜单项一样大（收起时约 44×40px），鼠标移上去有和菜单项相同的浅色底，并显示“展开菜单”/“收起菜单”提示。
3. 颜色比现在亮一档，与菜单图标同色，不再用暗灰。
4. 展开状态下按钮显示图标 + “收起菜单”文字；位置仍在菜单栏底部，展开后记住用户的选择（沿用第 10 项第 7 条）。

## v3 原型实现说明（与上文规则的差异和模拟方式）

- 原型中的“大模型”均为规则模拟：时间识别（`PA.parseWhen`）、自动打标签（`PA.autoTags`）、重新生成标签、批量完成的排除匹配，结果会有噪音，不代表真实模型效果。
- 重复文件判断：原型用“文件名 + 大小”模拟“内容相同”，用“大小完全相同、名字不同”模拟第 2 项情况 4；情况 2“另一个页面正在上传”在原型中按同一浏览器内的未完成上传判断；情况 3 由服务端兜底，只在上传确认框说明中体现。
- 第 5.3 项“参考用户风格”：原型只模拟一种风格信号（用户建的扁平标签，如「合同」）以及改名记录（`state.tagRenames`，防止改名后重新生成又加回旧名）。
- 第 6 项为试行：`reminders.html` 保留为跳转到助手页，便于旧链接访问。
- 第 7 项邮件“✓ 完成”链接：只在邮件预览中展示，原型里点击直接完成。

## v4 原型实现说明（与上文规则的差异和模拟方式）

- 与本说明相关的第 10 项各条均已在 `public/ITER1/v4/` 中实现；原型里所有“大模型”能力仍是规则模拟，结果会比真实模型粗糙。
- **问候改写**：程序先按“固定模板 + 待办数据”组好一句事实（几件、最早的时间与标题），再交给改写函数；原型只模拟“加开场”这一步——有节日就用节日祝语，没有节日就用天气开场，其余照抄模板。改写结果要过数字校验（输出里的数字与时间必须与模板完全一致），校验不过或改写报错、超过时限就退回模板。每个用户每天只生成一次，存在当天的对话记录里；当天数据变了就回到模板的实时内容。
- **节日表**：`PA.SEED.holidays` 里放两张表——农历节日按公历日期（`lunar`，如端午节）和固定日期（`fixed`，如 10-01）——由程序查表后告诉改写函数，不让模型自己判断节日；原型只覆盖演示日期附近的节日，不做到 365 天完整日历。
- **会议整理**：上传的会议录音识别完成后放入待确认会议数据（`state.inbox`）。助手主动发一条消息，写清是哪个录音、整理出几条待办、其中几条分给“我”。选“一起过一下”展开逐条勾选（默认勾选负责人是“我”的），每条可“听原话”；原话时间点取演示数据里的分句时间，没有的注明“这段录音没有逐句时间点”。确认后会议本身存成一条已完成的记录，勾选的行动项变成“待安排”新待办。
- **“晚点再说”的时间**：原型用 `PA_REMIND_MS`（默认 30 秒）代替真实延迟——选“晚点再说”时把会议标为等待，30 秒后再由助手发一条带“之前说晚点再看的会议”字样的提醒；刷新页面后仍会按等待状态补发，避免演示时等不到。
- **代写初稿**：从待办标题里识别周报 / 方案 / 介绍 / 总结 / 报告；在本人知识库里按名字（权重高）和正文命中找同类文档当参考，找不到就按通用格式写。素材只取演示数据里已有的内容：周报取本周已完成的待办、会议要点、想法记录、下周计划；其他类型取会议要点、相关待办、想法记录。素材不足的段落写成“还缺：……”，不自行编造数字和事实。初稿以 `.md` 存入知识库并挂到对应待办，同类事项连续拒绝 3 次后不再主动提示。
  - 参考文档得分相同时，优先用真实文档而不是模板，再优先用较新的。
  - 演示场景：知识库有上周的「工作周报」和「客户管理系统二期-项目介绍」。对助手说“下周三交周报”，助手提出参照上周周报来写；会议录音“客户需求沟通”里有一条分给我的“编写一份新的移动审批项目介绍”，确认加入待办后，助手说明知识库里已有类似的项目介绍，只需要用户提供项目信息。
  - 演示数据版本已升级，打开过 v4 的浏览器会自动重置一次 v4 演示数据，需要重新登录。
- **导出 .doc**：把初稿纯文本按行包成一段 HTML（`text/html` 的 Blob），用文件名“标题.doc”下载，Word 可以直接打开；不做真正的 .docx 排版、样式和页眉页脚。
- “最近安排”面板、对话记录、随用随提示等其余第 10 项内容按上文规则实现；历史对话只保留 30 天，面板内容不写入对话记录。
