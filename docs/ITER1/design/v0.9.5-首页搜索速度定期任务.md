# v0.9.5：首页、按意思搜索、速度、定期任务

- 日期：2026-11-12
- 状态：已定（用户 11-12 回复“都做”，未答的问题按建议执行）
- 范围：Go 后台（`server/`）+ iOS App（`ios-app/`，0.9.4 → 0.9.5）。Web 不动。

## 0. 实测结论（11-12）

- 后台处理一个请求只需 0.2～3 ms（65 日志里的 duration）。在 65 本机请求 `/api/health` 约 2 ms。
- 从外网经 Cloudflare 访问，同一个接口要 1.2～1.7 秒，TLS 握手约 0.7 秒。Tunnel 当前连在 tpe01/khh01。
- 结论：**慢在网络链路和请求次数，数据库没问题**。数据库已经是 65 本地的 SQLite，不经过 Cloudflare，不加 Redis 或 PostgreSQL。
- 优化方向：
  1. 减少请求次数：启动时合成一个请求，App 先显示本机缓存。
  2. 聊天改成流式，边生成边显示。
  3. 上传后立即开始处理，不再等下一个 5 秒轮询。

## 1. 后台接口（新增，旧接口保持不变）

### 1.1 `GET /api/home?msg_limit=10`
启动和回到前台时只调这一个接口，代替 `me` + `items` + `messages`。
```json
{ "user": {...同 /api/me...},
  "items": [...同 /api/items 全部未删除和已删除...],
  "messages": [{id,role,content,model,created_at}],   // home 线程最近 msg_limit 条（默认 10，最多 50），按时间正序
  "has_more": true,                                    // 更早还有消息
  "brief": {"kind":"morning|weekly","text":"...","created_at":"..."} | null,   // 今天（Asia/Taipei）最新一条简报
  "server_time": "..." }
```
响应在客户端带 `Accept-Encoding: gzip` 时用 gzip 压缩。gzip 对所有 `/api/` JSON 响应生效，但 SSE 接口除外。

### 1.2 `GET /api/messages?thread=home&limit=20&before=<created_at>`
在现有接口上加 `before` 参数：返回 `created_at < before` 的最近 `limit` 条，按时间正序。另返回 `has_more`。不带 `before` 时行为和原来一样，只是多返回 `has_more`。

### 1.3 `POST /api/chat/stream`
- 请求体和 `/api/chat` 相同。
- 响应 `Content-Type: text/event-stream`，并带 `Cache-Control: no-cache`、`X-Accel-Buffering: no`。每写一段都 Flush。
- 事件：
  - `data: {"delta":"..."}`，可以有多条；
  - 最后一条是 `data: {"done":true,"reply":"完整回复","model":"...","fallback":false}`。
- 上游请求带 `stream: true`。上游出错时发一条带兜底文字的 `delta`，再发 `done`（`fallback: true`）。
- 限流、存消息的逻辑和 `/api/chat` 相同：完整回复生成后，存成一条 assistant 消息。
- `llm.Client` 新增 `Stream(model, messages, opts, onDelta func(string)) (string, error)`。

### 1.4 `POST /api/ask` —— 按意思搜索
请求：`{"q":"帮我搜一下这个月需要处理的事情"}`，最多 200 字。

1. 用模型 `XIAOHE_MODEL_ASK`（默认 `deepseek-v4-flash`，15 秒超时）把这句话解析成 JSON。提示词里给出今天的日期（Asia/Taipei）和星期：
```json
{"from":"YYYY-MM-DD|null","to":"YYYY-MM-DD|null","kinds":["todo","watch","idea"]|[],"status":"open|done|any",
 "scope":["things","files","said"],"keywords":["..."],"answer_hint":"一句话说明理解成什么"}
```
2. 按解析结果查询：
   - **things**：items 里 kind 在 `kinds` 中（为空时默认 todo、watch、idea）、未删除、状态符合 `status` 的事项。有时间范围时，按 `due` 落在 [from, to] 筛选；`status=open` 时，to 之前已经过期但还没办完的也算进去。有关键词时，标题、备注、负责人里至少要命中一个关键词。最多 50 条，按 due 升序，没有 due 的排在最后。
   - **files**：录音和资料。有时间范围时，按 `recorded_at` 或 `created_at` 筛选；有关键词时，按现有关键词搜索逻辑匹配。
   - **said**：只在有关键词时查，逻辑和现有 `/api/search` 相同。
3. 返回：
```json
{"answer":"这个月还有 6 件没办完，其中 2 件已过期。","filter":{...解析结果...},"said":[],"things":[],"files":[],"mode":"ask|keyword"}
```
   - `answer` 由程序按结果生成，不再调用一次模型。
   - things 里每条的字段和 `/api/search` 相同，另加 `kind`、`due`。
4. 模型调用失败、超时或解析不出 JSON 时，退回关键词搜索：把整句去掉“帮我/搜/找/查/一下”等词后，用剩下的部分做关键词，`mode` 设为 `keyword`。
5. 关键词不写日志。

### 1.5 简报 `GET /api/briefs?limit=10`
返回本人最近的简报 `[{id,kind,text,created_at}]`。

### 1.6 管理端：定期任务
- `GET /api/admin/jobs`：每个任务的配置和最近 10 次运行（开始时间、耗时、处理用户数、结果或错误）。
- `PUT /api/admin/jobs/<name>`：请求体 `{"enabled":true,"at":"08:00"}`，存到 settings 表 `job.<name>`。
- `POST /api/admin/jobs/<name>/run`：立即运行一次（忽略防重复），用于测试。可以带 `{"user_id":"..."}`，只对这个用户运行。
- 只有 admin 能调用，并写 audit。

## 2. 定期任务（后台）

- 新增 `internal/jobs`（也可以放在 `api` 包里的 `jobs.go`，由实现者决定）。
- 每分钟检查一次，时区固定 Asia/Taipei。
- 防重复：新表 `job_runs(id, job, user_id, run_key, status, detail, started_at, finished_at)`，`UNIQUE(job,user_id,run_key)`。`run_key` 例如 `2026-11-12` 或 `2026-W46`。
- 服务启动时，如果今天的任务已经过了预定时间但还没跑，补跑一次；超过预定时间 3 小时就不再补。
- 新迁移 `0005_jobs.sql` 建两张表：`job_runs` 和 `briefs(id,user_id,kind,text,data,created_at)`，再加上索引。

| 任务 name | 默认时间 | 模型（环境变量，括号内为默认值） | 做什么 | 受“主动服务”影响 |
|---|---|---|---|---|
| `morning` | 每天 08:00 | `XIAOHE_MODEL_JOB`（flash） | 统计今天到期、已过期、等你定（kind=idea/stash）的事项。模型写 1～2 句简报，不编造，最多 80 字，存进 briefs（kind=morning）。没有任何事项时不生成 | on：存简报并推送；quiet：只存不推；off：不做 |
| `remind` | 每 5 分钟 | 不用模型 | 找出未删除、未办完、`data.remind_at <= 现在`、且 `data.reminded_at` 为空的事项，推送“提醒：<标题>”，然后把 `reminded_at` 写成当前时间（ISO） | 不受影响，用户自己要求的提醒照常推送 |
| `profile` | 每天 02:00 | `XIAOHE_MODEL_PROFILE`（pro，3 分钟超时） | 读这个用户前一天的 home 对话和当天完成的纪要摘要（合计截取不超过 12000 字），再把现有 fact 交给模型。模型只输出新增的事实，最多 5 条：`[{"text","group":"工作|健康","from":"来自：..."}]`。新事实建成 kind=fact 的事项（id 用 `fact-auto-<随机>`，`data.auto=true`），和已有 fact 文本相同的跳过。前一天没有对话也没有纪要时跳过 | off 时不做 |
| `weekly` | 每周五 17:00 | `XIAOHE_MODEL_JOB` | 统计本周办完的事、还没办完的事、新增的事。模型写 3 句以内的回顾，存进 briefs（kind=weekly） | 和 morning 相同 |

- 读取“主动服务”：items 里 `id='setting-proactive'` 的 `data.value`，没有时按 `on` 处理。
- 推送：把 `notify` 里发 APNs 的部分抽成通用函数 `pushUser(uid, title, body string, data map[string]string)`，录音推送也改用它，行为不变。payload 的 `body` 字段带 `{"type":"brief|remind","item_id":...}`。
- 所有模型名都从环境变量读，并有默认值。启动日志打印 `jobs enabled morning=08:00 ... models job=… profile=…`。
- `XIAOHE_JOBS=off` 时整体关闭，测试环境用。

## 3. 队列：上传后马上处理
API 加一个 `wake chan struct{}`，缓冲为 1。上传录音、语音或资料成功，以及重试时，用非阻塞方式发送一次。队列循环在 ticker 和 wake 两者中任意一个触发时运行 `ProcessOne`。一次处理完后，如果队列里还有任务，���即接着处理下一条，不再等 5 秒。

## 4. iOS 0.9.5

### 4.1 启动和速度
- `api.home(token, msgLimit)` 对应 1.1。`store.tsx` 里 `sync` 和启动逻辑改用 `/api/home`；返回 404 时退回旧的 `me` + `items` 方式。messages 和 brief 也放进 store，首页不再自己请求 messages。
- **本机缓存**：每次 home 成功后，用 `expo-file-system` 把 `{user, items, messages, brief, has_more}` 写到 `cache-home.json`（documentDirectory）。启动时如果 SecureStore 里有 token，先读缓存并立即显示（`ready=true`），再在后台调 `/api/home` 更新。不再先等 `/api/me`。返回 401 时清掉缓存和 token，回到登录页。退出登录时也删缓存。
- **流式聊天**：用 `import { fetch } from 'expo/fetch'` 请求 `/api/chat/stream`，读取 `response.body.getReader()`，按 SSE 格式解析，边收边更新最后一条 assistant 气泡。失败时退回 `/api/chat`。“小禾正在想…”在收到第一个 delta 后消失。

### 4.2 首页（00）
- 首页只显示最近 **10** 条对话（来自 home），加上本次会话里新发的消息。
- 有 `has_more` 时，对话区顶部显示一行可点的“查看更早的对话”。点一次用 `before=最早一条的 created_at` 再加载 20 条，插到前面，并保持当前滚动位置，不跳到底部。
- 简报卡片下方显示 `brief.text`（今天有简报时），小字，颜色用 t2。

**录音结束后的提示（按住说一句）**：
1. 松手、上传成功后：先震动（Success），再从屏幕顶部弹出一条提示“收到，正在转成文字”，显示 1.5 秒后自动消失。提示出现约 0.8 秒后，再滚到这条语音气泡。
2. 处理完成、拉到回复后：弹出提示“小禾回复了”，再滚到回复的位置。不要用原来那种内容一变就立刻滚到底的方式。
3. 处理失败时：提示“这条语音没能处理，点气泡重试”。
4. 提示做成通用组件 `components/Toast.tsx`，通过 `toast(text)` 调用，用 Animated 实现，不加新依赖。样式和现有主题一致：卡片底色、圆角、小字，不用渐变。

**会议录音**（`records.tsx`）：
- 录完或导入、上传成功后，弹出提示“录音已上传，正在整理”。
- 列表刷新后滚到新的那一条，并把这一行的背景高亮约 2 秒。

### 4.3 搜索（01）
- `api.ask(token, q)` 对应 1.4。
- 搜索页（`search.tsx`）的判断规则：输入包含空格，或长度 ≥ 6，或包含“本月/这个月/这周/本周/今天/明天/下周/需要/要办/没办/过期/帮我”中任一词，就当作一句话处理。这种情况不随输入自动搜，要按键盘的“搜索”键或点“问小禾”才调 `/api/ask`。其它输入维持原来的关键词自动搜索。
- `/api/ask` 的结果：顶部用一行显示 `answer`，下面的分组和关键词搜索相同（事情、说过的话、资料），事情多显示一个 due。
- “试试搜”里加两个整句示例：“这个月需要处理的事情”“这周开会说要办的事”。
- 录音页（`records.tsx`）顶部加一个搜索入口，样式和搜索框一致，只能点不能输入，文字是“搜录音、纪要、要办的事”。点击后进入 `/search`，并带参数 `scope=records`。带这个参数时，占位文字改为“比如：上周例会说要办的事”。
- 首页聊天：消息以“搜/查/找/帮我搜/帮我找/帮我查”开头时，不走聊天，改调 `/api/ask`。把 `answer` 和前 5 件事做成一条 assistant 气泡（每件一行：“· 标题（到期）”），后面跟一行可点的“看全部结果”，点击跳到 `/search?q=原句`。搜索页读到 `q` 参数时立即发起 ask。这条结果只显示在本地，不存到服务器。

### 4.4 稍后再提醒
- “逐件过”里点“稍后”时，除了先跳过这一件，还把该事项的 `data.remind_at` 设成提醒时间：今天 17:30（本地时间）；如果现在已经过了 17:00，就设成明天 09:00。用 store 现有的 upsert 或 moveItem，并清掉 `reminded_at`。
- 该事项下次打开时显示“17:30 再提醒”或“明天 9:00 再提醒”。
- 后台 `remind` 任务到时间会推送提醒。

### 4.5 推送点开
`data.type=brief` 时跳到首页；`data.type=remind` 并带 `item_id` 时跳到 `/watch`。
